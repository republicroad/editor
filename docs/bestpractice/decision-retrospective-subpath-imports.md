# 决策复盘：为什么 Subpath Imports（`#` 前缀）不是第一推荐

> 2026-09-03 沉淀。这不是一篇技术规范，而是一次**决策过程的完整复盘**——
> 记录"内核别名方案"从桥（C）到 `@kernel/*`（A′）再到 `#` imports（D）的
> 演进全程：每一轮的已知/未知、当时的取舍理由、以及事后看D为什么
> "明明存在却没有第一时间被推荐"。
> 写作目的：未来遇到同类方案选型时，按此复盘的教训清单自查。
> 技术细节的规范表述见 [别名机制对比](./monorepo-alias-mechanisms.md)。

---

## 1. TL;DR

**D（`#` subpath imports）不是一开始不推荐，而是"推荐 D 所需的约束条件"在当时尚未完备。**
三个条件依次被追问补齐：① 任意宿主的源码直通零碰撞（排除 A′）② 不引入永久纪律成本
（排除 A）③ 解析锚定到各自 package.json（正是 D 的规范定义）。需求精确化到第三条时，
答案才浮现。**过程的工程价值不在"最终选了什么"，而在复盘沉淀的五条可迁移教训（§5）。**

`#` 保留前缀）的规范定义。**约束条件的完备化是方案 D 出现的直接原因。**

## 3. 为什么 D 不是第一推荐：四层原因

### 3.1 生态成熟度时间线不利

`paths` 别名是十余年的共识，Nx/Turbo 教程遍地、工具链全谱理解一致。
`#` subpath imports 是生态的**新角落**：

| 工具 | `#` 支持 | 说明 |
| --- | --- | --- |
| TypeScript（类型解析） | 5.4+（bundler/node16 解析模式；以官方发布说明为准） | 本仓 5.9.3 ✅ |
| Vite（运行时 + lib 构建） | 5.1+ | 本仓 7.x ✅ |
| bun（运行时 + test） | ✅ 原生（按最近 package.json） | 本仓 1.3.14 ✅ |
| esbuild / webpack | ✅ / ✅ | — |
| **shadcn/reui CLI（写入侧）** | **未知**——aliases 校验对 tsconfig `paths`，`#` 不在其中，可能拒绝 | **spike 待验证** |

在内核冲刺 0.3.0 的背景下，第一优先级是"零内核改动的桥先把集成跑通"，
而非踩一条文档稀疏、CLI 支持未知的路。

### 3.2 D 当时有三个未闭名的缺口

1. **CLI 写入口径**：shadcn/reui 装机按 components.json aliases 写导入，`#` 是否被
   CLI 接受未验证。兜底方案存在（tsconfig 保留 `@kernel/*` paths 专供 CLI 写入，
   代码实际走 `#`，双轨无碰撞——`@kernel` 与宿主 `@/` 不同名），但复杂度上升一档。
2. **发布分布面**：内核 lib 构建时 `#` 被 vite 就地解析（dist 零残留 ✓），但生成的
   d.ts 若保留 `#` 引用，随包发布的 package.json imports 字段需含生产映射——
   分布约束需要 spike 观察。
3. **工具链版本地板**：全链（TS/Vite/bun/编辑器）都须在支持版本之上。对本仓无碍
   （全部满足），作为"对外推荐的最佳实践"则是约束。

相比之下，A′ 的已知弱点（前缀碰撞）是低概率理论项，桥（C）则是零改动实证稳定——
**未知缺口 vs 已知小概率弱点**，当时的理性选择是后者。

### 3.3 相对导入（A）也不等于答案

"不是有相对导入么？"——相对导入从一开始就在选项里，未被首选的原因是**持续摩擦**：

- shadcn CLI **无法写相对导入**（生成器不知道文件最终深度，`cn` 导入在
  `ui/button.tsx` 与 `comp-xyz.tsx` 的相对层数不同）——76 文件改完之后，
  **每次装机都要 codemod 擦除**，永久纪律成本。
- 深目录 `../../../` 可读性税。

D 的价值恰恰是**合成了两者**：像相对导入一样按包锚定、零碰撞；
又像别名一样有稳定 specifier、生成器可写（待 spike）。
**D 是"相对导入的规范化形态"——这个综合视角，需要先看清 A 的缺点与 C 的局限才会出现。**

### 3.4 最小爆炸半径先行

桥（C）的落地成本是**零内核改动 + 宿主侧一个 tsconfig**，且被两批次内核迭代
（v0.2.2→v0.3.0 期间 19 commits）实证稳定。方案选型的第一原则是**用最小爆炸半径
把集成跑通，为方案演进争取信息**——桥不是绕路，而是给 D 的成熟与需求的显式化
**争取了时间窗**。

## 5. 可迁移的工程教训（本复盘的核心产出）

1. **最优解随需求精确化浮现**。把"约束条件的完备化"当作方案切换的触发器，
   而不是在约束模糊时强行排序方案。R6 的"按各自 package.json 解析"一句话
   完成了 A′→D 的切换判据。
2. **先隔离后收敛**。适配层（桥）的价值不只是解决当下，而是**为正确方案的
   成熟与需求的显式化争取时间窗**。桥从未被当作终态，但它是所有后续讨论
   能够安全进行的前提。
3. **方案落地前，用 spike 证伪最大不确定项**。D 的最大未知是 CLI 行为——
   半小时级的 spike（一条 imports 映射 + 改一个文件 + 四端验证）排在全量
   迁移之前，失败成本被锁定在最小。
4. **引入生态新特性要查工具链全谱**：类型解析 / 运行时 / 构建 / **生成式工具
   的写入侧**——最后一项最易被遗漏（CLI 不是解析器，是代码生成器，它的
   校验逻辑有独立的兼容面）。
5. **外部可消费的包，包内命名按"最坏宿主"设计**。任何进入源码分发的名字
   （别名、全局变量、CSS 类）都是强加给所有未来宿主的税——tsc paths 是
   程序级全局名，`@kernel` 也只是缩小赌注，`#` 才是规范级出清。
