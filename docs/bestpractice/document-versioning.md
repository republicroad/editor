# 文档多版本：业界实践与本仓实现

> 2026-09-05 沉淀。规则历史功能（第五十~五十二批）落地后，对业界"文档多版本"
> 实现的系统性对照——回答：业界怎么做、本仓做对了什么、下一步往哪走。
> 与[发布手册](./release-process.md)的辨析：本篇讲**文档版本**（规则图的编辑历史），
> 发布手册讲**发布版本**（semver/包版本）——两者机制完全不同，业界从不混用。

---

## 1. 四种主流架构（按复杂度递增）

| 架构 | 代表产品 | 原理 | 优 | 劣 |
| --- | --- | --- | --- | --- |
| **① 整状态快照池** | Confluence 页面历史、Notion 页面历史、**本仓现行** | 每版本存完整文档状态（JSON）；head + 历史池 + 保留策略 | 简单可靠、天然可回放、无专用基础设施 | 存储随版本线性增长、diff 需加载成对版本 |
| **② 快照池 + 命名/自动分层** | **Google Docs**、**Figma**、SharePoint（major/minor 配额） | ①基础上分两类：**用户命名版本（永久）+ 自动检查点（治理修剪）** | 体验最好（自动兜底 + 人工标记里程碑）、存储有界 | 需要保留策略引擎 |
| **③ 操作日志（OT）** | Google Docs 底层 | 存**编辑操作序列**而非状态；版本 = 日志上的位点；定期压缩出快照 | 每次编辑存储极小、天然精细 diff/undo | 重基础设施、需要压缩、跨会话恢复复杂 |
| **④ CRDT** | Yjs（AFFiNE/BlockSuite）、Automerge | 文档 = CRDT 状态；版本 = 状态向量快照；天然多端合并 | 实时协同 + 离线合并免费 | 引入 Yjs/Automerge 级依赖与数据模型重构 |

**选择规律**：单用户/保存制编辑器 → ①②；实时多人协同 → ③④。
**本仓处于 ①→② 的正确位置**，不需要 ③④——那是实时协同的需求信号出现后才值得的迁移。

## 2. 业界产品在"快照池"上的共同设计决策（七条）

| # | 决策 | 业界做法 | 本仓现状 |
| --- | --- | --- | --- |
| 1 | **版本分两层**：自动检查点（治理修剪）+ 命名版本（永久） | Google Docs/Figma/SharePoint 一致 | ✅ auto/manual（第五十二批）；命名版本在 backlog |
| **2** | **恢复不可破坏**：恢复旧版本 = 复制为最新版本，绝不在原地删除其后版本 | Google Docs/Figma/Confluence 一致（"restore is forward"） | ⚠️ 规划中（第五十三批交付物 3） |
| 3 | **保留分层**：自动版按数量/时间修剪，命名版永久 | Google Docs 按账期分层；SharePoint major/minor 配额 | ✅ 数量上限（20 auto + 全部 manual）；时间分层为精化方向 |
| 4 | **命名版本**：用户给保存命名，历史按名检索 | Google Docs/Figma 标准能力 | 🔜 第五十三批（versionName 全链） |
| 5 | **版本对比**：任选两版渲染差异 | Confluence 任意两版、Google Docs 可视化 diff | 🔁 已立项移交内核会话（graph-diff-spec） |
| 6 | **存储治理**：版本压缩（gzip）、内容寻址去重 | git/Figma 内部 | 未做（JSON 明文，量小先不做） |
| 7 | **undo/redo 与历史分离**：会话内撤销栈 ≠ 跨会话版本历史 | 全业界一致 | ✅ 已遵循 |

## 3. 三条界外警告（不要做的）

1. **操作日志/OT**：只有实时多用户协同成为需求才值得——是产品形态变化，不是功能叠加。
2. **CRDT（Yjs/Automerge）**：同上；且引入重量级数据模型依赖。
3. **文档 git 化**（每图一个 git 仓）：运维成本/体积/并发锁全不合适。

## 5. 保存边界的本质判断

业界产品的"保存"定义 = **数据 + 会话现场**一体持久化（Figma 保存画布+视口；Google Docs
保存文档+会话上下文）。本仓第五十批把 `session`（viewport/页签/草稿）纳入
`content.session` 恰好对齐——**"保存边界"从"数据"扩展到"数据+现场"，这是所有
业界产品的共同演进路径**，也是规则历史重设计的根本动机。
